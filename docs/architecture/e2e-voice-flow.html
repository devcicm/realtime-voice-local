4. Pipeline TTS + protocol v2

El servidor TTS emite los eventos del protocol v2. En cada chunk de Piper, envía un header JSON audio_chunk antes del frame binario PCM. El campo word_offsets_ms en audio_end es lo que permitiría al cliente iluminar palabra-por-palabra.

protocol_versions 1 2 C->>WS: send tts text chunk_id proto 2 WS->>P: process_tts_request P->>B: generate_streaming text lang speed loop for each Piper chunk P-->>WS: chunk WS-->>C: audio_chunk chunk_id seq
sample_offset samples duration_ms WS-->>C: bytes PCM f32 16kHz end P-->>WS: chunk final WS-->>C: audio_end chunk_id
word_offsets_ms duration_ms
word_count WS-->>C: audio_end final true
Protocol v2 consumido en el monolito (resuelto — build c):
  • audio_start — consumido (set request_id + activeRunId, reset buffer, toma word_offsets_ms)
  • audio_chunk JSON — consumido como metadata (línea 2681): se guarda en pendingAudioChunk y NO se reproduce como PCM
  • audio_end — consumido (log, schedule playback, toma word_offsets_ms)
  • frames binarios PCM — reproducidos solo si hay run activo (fence anti-stale, línea 2691)
El campo word_offsets_ms alimenta el truncate de la ConversationLog durante el barge-in (línea 3539).

5. Ciclo de vida del ConversationLog

Cuatro estados posibles por turno. La diferencia crítica entre interrupted y canceled es que el primero se mantiene en el contexto del LLM (comunicación fluida) y el segundo se borra (privacy mode).

stateDiagram-v2 [*] --> streaming: streamUserPartial streaming --> streaming: update partial streaming --> finalized: commit
or addUserTurn streaming --> finalized: addAssistantTurn finalized --> interrupted: mark_interrupted finalized --> canceled: cancel_finalized streaming --> canceled: cancel_stream canceled --> [*] interrupted --> finalized: idempotent re interrupt note right of interrupted interrupted se preserva en to_messages el LLM ve el partial comunicacion fluida end note note right of canceled canceled se EXCLUYE de to_messages sintetico solo si cancelMode es note o summary end note

Modos de cancelación (sólo aplican a canceled)

ModoComportamiento
silentEl turn se borra sin inyectar nada. Privacy total.
note (default)Inyecta system turn: [Previous assistant response was interrupted. Partial content: ...]
summaryInyecta system turn con la primera oración del partial.

6. Flujo de barge-in

Cuando el usuario habla mientras el asistente está sonando: el audio local se corta, el LLM stream se cancela, el TTS deja de enviar chunks, y el partial del asistente queda en la ConversationLog marcado como interrupted para que el próximo turno del LLM tenga contexto.

ws.binary frames en queue U->>Mic: empieza a hablar Mic->>M: vad.speech.start M->>M: stopGeneration
currentSource.stop
audioQueue = empty
playbackTimer = null M->>WS: ws.send type interrupt WS-->>WS: cancel stream reader WS-->>M: deja de enviar frames M->>Log: log.mark_interrupted

el partial del asistente en el contexto U->>Mic: termina de hablar Mic->>Mic: encode WAV Mic->>M: STT transcribe M->>M: STT response text M->>Log: addUserTurn finalized Log->>M: conversationLog.toMessages sys M->>M: POST llm chat completions
messages incluye partial asistente
Configuración (ConfigStore): cancelOnInterrupt = true cambia el comportamiento a privacy mode (cancel_finalized en vez de mark_interrupted). Por default es false (interrupted, comunicación fluida).
Resuelto en build b/c (barge-in Gold): stopGeneration() (línea 3464) ahora ejecuta el cancel end-to-end: anti-loop rate limiter, stop de audio local + vaciado de colas, MessageBus.emit(INTERRUPT) (aborta LLMStage con AbortController), ws.send {type:'interrupt', run_id, reason}, conversationLog.truncate(playedAudioMs, wordOffsetsMs) + mark_interrupted('assistant','barge-in') (línea 3539-3544), activeRunId = null (los frames binarios tardíos se descartan en la línea 2691) y re-arm del mic (FSM → INTERRUPTED → RECORDING).

7. Propagación de trace_id

El TraceMiddleware de FastAPI abre un span por request HTTP/WS y setea trace_id en un contextvar. Un thread watcher copia ese valor a un contextvar separado que el logging.Filter inyecta en cada LogRecord. Resultado: un grep "trace=abc-123" muestra todo el flujo de una sesión en los logs.
